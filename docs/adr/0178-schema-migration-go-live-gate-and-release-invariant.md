# Three setupAll() guards ship as the go-live gate; the full migration runner is committed, sequenced, and release-invariant-enforced — never deferred as optional

Status: accepted

Issue #58's 8 CEO-review hard requirements are non-negotiable additions, not optional expansions — none may be dropped from the eventual implementation plan. But they don't all share the same trigger: `setupAll()` calls `Setup_ensureAllTabsExist` and `Setup_applyValidationsAndProtections` unconditionally on every invocation (`Setup.js:19-28`), regardless of whether a deliberate schema migration is happening — so the header-mislabeling hazard (ADR 0176), the `LEDGER_ID`-vs-active-spreadsheet mismatch hazard, and the stale-protection/capped-validation hazard (ADR 0177) are live today, independent of any migration event. The remaining requirements (versioned journal/rollback, per-ledger `SCHEMA_VERSION` with fingerprint validation, AnnualMigration wiring, and the `setMemberSelections`/`activateMigration` race-condition locks) only matter once a deliberate column-layout change or Annual Migration actually runs — and #55 already locked that neither happens in the go-live window.

**Decision:** sequence, don't drop. Phase 0 — the three `setupAll()` guards — ships as the go-live gate, using a two-pass ordering: the `LEDGER_ID` reconciliation guard runs first; then a read-only preflight pass over every pre-existing tab (collecting every ambiguity across all tabs before deciding); only if that pass is fully clean does a second pass create/initialize missing tabs and leave already-canonical existing tabs untouched. Phase 1 — the full versioned migration runner, `SCHEMA_VERSION` tracking, AnnualMigration wiring gate, and race-condition locks — is committed follow-on work in the same policy, not an open-ended "maybe later."

**Release invariant:** no deployment before Phase 1 ships may change any `COLS` layout or invoke a schema-affecting migration. The Phase-0 guards alone cannot enforce this — they only fire inside `setupAll()`, not on ordinary `Api.js`/`Engine.js` runtime calls, so a code change to `COLS` without a matching migration and without a `setupAll()` re-run would silently corrupt reads/writes with no abort anywhere. This invariant is a process discipline (code review must reject any `COLS` diff before Phase 1 exists), not something Phase 0 alone guarantees.

## Consequences

A migration is not reported SUCCESS on data movement alone. Audit.append() (Audit.js:61-62) independently acquires LockService.getScriptLock(), so calling it while the migration still holds its own script lock risks a reentrant-lock deadlock this codebase has no verified-safe pattern for; the manifest append (migration ID, before/after SCHEMA_VERSION, per-tab final fingerprints, row counts) to the same ledger's AUDIT_LOG (there is no separate source/target ledger here, unlike Annual Migration; schema migration restructures one ledger in place) via Audit.append() must happen strictly after lock.releaseLock(). Audit.append()'s hash-chaining logic itself is untouched; the one addition it needs is covered below.

That ordering constraint doesn't make the manifest optional: the migration reports one of three outcomes, not two. SUCCESS only once data movement, manifest append, and a post-append Audit.verifyChain() all succeed. MANIFEST_INCOMPLETE if data movement finished but the manifest append or the post-append verifyChain() failed; FAILED/ROLLED_BACK per ADR 0177 if data movement itself didn't complete. MANIFEST_INCOMPLETE is loud, not silent, unlike the Discord-notification posture (a delivery failure never blocks or is reported back against the transition it describes), because the manifest is the exact artifact #58 and the staging checklist require as proof of a successful migration, not a side notification.

Audit.append() has no deduplication: it always computes a fresh seq/hash and appends unconditionally, with no lookup for "has this already been recorded." A scan-then-append performed by the caller cannot close this safely. Two concurrent MANIFEST_INCOMPLETE retries could both scan, both find nothing, and both append. The check-then-act race is real, and wrapping the caller's own scan+append in a second LockService.getScriptLock() would reintroduce the same reentrant-lock risk this design already ruled out, since Audit.append() acquires its own lock internally.

Audit.append() gains one new, optional parameter instead: idempotencyKey. Existing call sites (every Engine.js mutation) omit it and are completely unaffected. This is not a schema change; COLS.AuditLog has no dedicated key column, only the existing free-form detail field. When idempotencyKey is present, Audit.append() writes it as a reserved key inside detailObj (detailObj.idempotencyKey = idempotencyKey, serialized into the same detail JSON string every row already carries) and, inside the SAME critical section it already holds via its own lock, scans existing rows for one whose entityType/entityId/action match and whose parsed detail.idempotencyKey equals the given key. No new lock, no reentrancy, no race window, no schema change. The migration manifest call passes the migration ID as this key (entityType "SchemaMigration", action "MIGRATION_COMPLETE", idempotencyKey = migration ID); if a matching row is found, Audit.append() returns that row's existing {rowHash, seq} without appending a duplicate. A retry after MANIFEST_INCOMPLETE simply calls Audit.append() again unconditionally with the same idempotencyKey. The function itself, not the caller, guarantees at most one manifest row per migration.

Audit.append() also resolves AUDIT_LOG via the ambient global LEDGER_ID (Config.js:20-28), never an explicit target spreadsheet, so the manifest append is additionally constrained to only ever happen once LEDGER_ID already points at the ledger that was migrated. For a standalone schema migration (restructuring the currently-live ledger in place) this holds throughout with no extra step. For the AnnualMigration-integration path (requirement 7), the pre-activation Migrate_run/Setup_* pass runs on the new ledger while LEDGER_ID still points at the old one; its manifest must not be appended yet, or it lands in the wrong ledger's audit log. That manifest append is deferred until activateMigration successfully repoints LEDGER_ID, and happens as part of (or immediately after) activation, never before.

This manifest becomes required evidence in docs/staging-release-evidence-checklist.md's "Schema Migration" section once Phase 1 ships and a migration is actually exercised in staging.
