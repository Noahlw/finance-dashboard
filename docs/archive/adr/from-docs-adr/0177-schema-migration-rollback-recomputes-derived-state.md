# Schema migration rollback restores data by snapshot, but recomputes formulas/protections/validations

Status: accepted

A schema migration step is one of two kinds: `DATA_MOVE` (column reorder / value migration; real business data with no way to re-derive it) or `DERIVED_REAPPLY` (formula registry, validation rules, protection policy; all deterministic functions of a specific schema-version's column layout, not data).

`DATA_MOVE` steps journal `pre_step_values` (the exact range's prior values, chunked across journal rows or spilled to Drive if a single range would exceed a sheet cell's character limit) before writing, and roll back by restoring that snapshot into the same range. `DERIVED_REAPPLY` steps are never snapshotted — a `getRange().getValues()` capture does not include formulas (`getFormulas()`), `DataValidation` rules, or `Protection` metadata, so a values-only restore would leave stale/wrong formulas and protections in place after any rollback. Instead, rollback of a `DERIVED_REAPPLY` step re-invokes the same forward function against the tab's layout as of the schema version being rolled back to, not against whatever the currently-deployed code's COLS says.

A deliberate migration exists precisely because someone already changed COLS in code to the target layout and deployed it before running the migration, so "current deployed COLS" describes the new layout for the migration's entire duration. If a DATA_MOVE step then fails and rolls back to the old physical layout, naively reapplying "the registry" using current COLS would apply new-layout-shaped formulas, validations, and protections onto the just-restored old-layout columns — exactly the corruption this policy exists to prevent. The formula/validation/protection registry is therefore keyed by schema-layout version, not flat or single-version: REGISTRY[schemaVersion] maps to {formulas, validations, protections} per tab, retaining at minimum the current and immediately-prior version's entries (a migration only ever moves one version forward at a time, so rollback only ever needs those two). A DERIVED_REAPPLY step, forward or rollback, always applies the registry entry for the specific schema version of the layout it is targeting — the target version going forward, the source version on rollback — never implicitly "whatever COLS currently is."

This replaces reliance on the existing `Setup_applyProtections`/`Setup_applyDropdown` helpers, which are not idempotent as originally written: `Setup_applyProtections` skips re-applying a protection that already exists (leaving a stale one in place after a reorder), and `Setup_applyDropdown` validates only rows 2–1000 (a hardcoded cap, not tied to the sheet's actual size). The migration-safety `DERIVED_REAPPLY` step is a new drop-and-recreate policy: clear every existing protection and data-validation rule across rows 2 through `sheet.getMaxRows()` (not `getLastRow()`, which only covers populated cells and would leave stale rules parked below the last row), then recreate the registry-defined set across that same range. The code-defined formula/validation/protection registry is treated as the complete, authoritative source for every tab — there is no mechanism to preserve a manually-added protection or validation rule that exists only on the live sheet and not in code.

## Considered options

Snapshotting `Protection`/`DataValidation` objects for literal restore was considered and rejected — both are richer than a values grid (editors, warning-only flags, criteria objects) and serializing/restoring them faithfully is real new complexity for no benefit, since recomputing from the version-keyed registry is correct in both the forward and rollback direction, provided each recompute uses the registry entry for the layout it targets rather than defaulting to the latest deployed version.

## Consequences

Any protection or validation rule a Treasurer might add by hand outside the registry will be silently removed on the next `setupAll()` or schema migration run. If hand-added rules are ever needed, they must be added to the registry, not the live sheet.
