# Initial production go-live is owner-approved against staging checklist evidence, as a one-time gate

Status: accepted

ADR 0090 already locks the mechanism: production deployment requires an explicit release action, ordinary merges must not deploy automatically. It never names who performs that explicit action or what evidence must exist first. This ADR fills that gap for the initial cutover only, distinct from #55's migration authority (which gates schema migrations specifically, by data-corruption blast radius) and distinct from ADR 0090 itself (which remains the permanent, general mechanism for every production deployment thereafter).

**Decision:**

1. **Approver:** the spreadsheet owner, and only the spreadsheet owner, approves the initial production go-live. This lands on the same role as #55's migration authority, but is a separately made decision for a different risk class — #55 is about preventing accidental data corruption during a schema change, this is about judging whether the product is operationally ready for real committee use. They happen to share an approver; that is not an inheritance.
2. **Evidence:** the staging deployment's `clasp deploy` ID and public Web App URL, recorded inside the already-locked `docs/staging-release-evidence-checklist.md` (Treasurer-owned, per #59, triggered once all pre-launch blockers merge). No git commit SHA or clean-worktree verification is required — this is an accepted gap: the record proves a specific Apps Script deployment was live and checklist-verified, not which exact commit built it. A dirty-tree push between build and `clasp push` would not be caught by this evidence trail.
3. **Record:** the approval itself is recorded as a GitHub comment on issue #64, posted at the actual go-live moment — distinct from the comment that closes #64 now, which only records this policy decision (who/what/where/scope), not an approval, since go-live has not happened yet. GitHub permits commenting on a closed issue, so no reopening is needed when the real approval lands. No new `docs/` artifact was created for this, since none already existed and inventing one for a single event was judged not worth the new surface.
4. **Scope: one-time only.** This ADR governs the initial production cutover exclusively. It does not extend ADR 0090 into a permanent named-approver-plus-evidence requirement for every subsequent production deployment. After the initial go-live, ordinary production deploys are governed by ADR 0090's existing mechanism alone — an explicit release action, no named approver, no staging-checklist evidence requirement beyond what ADR 0090 already implies.

## Consequences

A later session can verify this was followed by checking: (a) a comment on issue #64 posted at the actual go-live moment (not the comment that closed #64 when this policy was decided) names the approving owner, (b) that comment or the linked checklist references a specific `clasp` deployment ID and Web App URL, (c) `docs/staging-release-evidence-checklist.md` was fully checked off at that time. Until that go-live comment exists, this ADR's policy is locked but not yet exercised — go-live has not happened. Because scope is deliberately one-time, this ADR does not need re-verification for deployment #2 onward once it is exercised — ADR 0090 alone governs those, and no future session should expect a per-release owner-approval comment to exist unless a later decision explicitly extends this one.
