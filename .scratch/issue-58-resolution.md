## Grilling + CEO Plan Review resolution: Schema Migration & Upgrade Safety Policy

Full policy locked across [ADR 0176](https://github.com/Noahlw/finance-dashboard/blob/main/docs/adr/0176-schema-migration-canonicalizes-by-numeric-column-index.md), [ADR 0177](https://github.com/Noahlw/finance-dashboard/blob/main/docs/adr/0177-schema-migration-rollback-recomputes-derived-state.md), and [ADR 0178](https://github.com/Noahlw/finance-dashboard/blob/main/docs/adr/0178-schema-migration-go-live-gate-and-release-invariant.md). All 4 original grilling questions answered; all 8 CEO-review hard requirements committed (none dropped) with an explicit sequencing decision.

### Answers to the 4 original questions

1. **SCHEMA_VERSION tracking:** stored as a `Config`-tab row inside each ledger's own workbook (per-ledger, never a global ScriptProperty). Validated against live tabs via a structural fingerprint (numeric COLS-position header shape per tab), not trusted from the stored number alone.
2. **Ambiguous-header handling:** hard-abort the entire call — zero writes anywhere — on any duplicate/unknown/missing/mismatched-position header, with a structured per-tab/per-column diagnostic. A brand-new empty tab is exempt (nothing to canonicalize against); only pre-existing tabs are preflighted, and only in a read-only first pass before any write in the same call (ADR 0176, ADR 0178).
3. **Journal + resume/rollback:** two step types — `DATA_MOVE` (journals `pre_step_values`, chunked/Drive-spilled if oversized; rollback restores the snapshot literally, including any `PENDING`/`FAILED` step, not just `DONE` ones) and `DERIVED_REAPPLY` (formula registry, validation, protections — never snapshotted; rollback re-invokes the same forward drop-and-recreate function against the current layout, since these are pure functions of `COLS`, not data) (ADR 0177).
4. **Audit/verification record:** a migration reports `SUCCESS` only once data movement, an `AUDIT_LOG` manifest append, and a post-append `Audit.verifyChain()` all succeed — not on data movement alone. The manifest append happens strictly after the migration's own lock releases (avoids a reentrant-lock deadlock risk with `Audit.append()`'s internal lock), is idempotent via a new optional `idempotencyKey` parameter on `Audit.append()` (persisted inside the existing `detail` JSON field, checked atomically inside `Audit.append()`'s own lock — no schema change, no new lock), and is deferred until `LEDGER_ID` actually points at the migrated ledger (relevant for the AnnualMigration-integration path, where the pre-activation pass runs against a ledger `LEDGER_ID` doesn't point at yet). Feeds a new "Schema Migration" section in `docs/staging-release-evidence-checklist.md`.

### Scope decision (CEO Plan Review)

Requirements don't share one trigger. `setupAll()` calls its header-write and protection/validation-apply paths **unconditionally on every invocation**, regardless of any deliberate migration — so 3 of the 8 requirements (canonical header preflight, `LEDGER_ID` reconciliation guard, drop-and-recreate protections/validations) are live hazards today. The other 5 (versioned journal/rollback, per-ledger `SCHEMA_VERSION`, AnnualMigration wiring, race-condition locks) only matter once a deliberate schema change or Annual Migration runs, which #55 already excluded from the go-live window.

**Locked: sequence, don't drop.** Phase 0 (the 3 `setupAll()` guards) ships as the go-live gate. Phase 1 (the full runner) is committed follow-on work in the same policy, not optional or open-ended — gated by an explicit **release invariant**: no deployment before Phase 1 ships may change any `COLS` layout or invoke a schema-affecting migration, enforced as a code-review discipline since Phase 0 alone can't catch a `COLS` change that never triggers a `setupAll()` re-run.

Closing #58.
