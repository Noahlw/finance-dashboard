## What to build

`ClaimsView.tsx` lets a Treasurer save a Claim as DRAFT, but provides no way to resume one across sessions. Specifically:

1. `draftId` state (`ClaimsView.tsx:63`) is populated only inside the same live session that calls `saveClaimDraft` (`ClaimsView.tsx:274` — `setDraftId(draft.claim_id)` inside `handleSave`'s save-draft branch). On a fresh mount, the only state restored from the backend is `claims[]` via `loadClaims()` → `apiService.getMyClaims()` (`ClaimsView.tsx:108-119`); `draftId` is left `undefined`. Closing the tab, reloading, or navigating away loses the in-progress draft entirely.

2. DRAFT-status claims DO appear in the claims table at `ClaimsView.tsx:824-859` (because `api_getMyClaims` at `Api.js:94-159` does not filter by status), but the row renders as read-only cells: `claim_id`, claimant, amount, status badge, submitted-at, receipt count. There is no click-to-edit / Resume affordance on the row.

3. `api_getMyClaims` (`Api.js:144-151`) returns only six fields per claim — `claim_id`, `claimant_id`, `notes`, `status`, `submitted_at`, `total_amount`. The columns needed to actually resume the form (`event_id` col 19, `expense_date` col 17, `semester` col 18, `payout_method` col 20, `payout_handle` col 21, per Constants.js:137-159) ARE persisted by `api_saveClaimDraft` (`Api.js:1203-1251` writes `event_id`, `expense_date`, `semester`, `payout_method`, `_paymentHandle(payload)` on update; new rows get them in the same column positions in `_appendRow`). They just are never returned to the client. Additionally, the draft's saved receipts live in `ClaimLineItems` (per-`receipt_id` + `budget_line_id` per Constants.js:119-127, written at `Api.js:1276-1310`) and are also not returned to the client today.

4. `payout_handle` is `JSON.stringify({ method, phone?, account?, details?, qrDriveFileId? })` per `_paymentHandle` (`Api.js:986-992`) and `_paymentDetails` (`Api.js:964-984`). FPS encodes `phone` + `account`; PAYME encodes `phone`; OTHER encodes `details`. So the saved `payout_handle` is round-trippable into the form's `fpsPhone` / `fpsAccount` / `paymePhone` / `otherDetails` fields, but only client-side via `JSON.parse` — the backend just returns the raw string.

This ticket wires the missing UI on top of a minimal backend shape extension:

- **Backend (Api.js):** add a thin `api_getClaimDraft(claimId)` (operator-auth, DRAFT-status-only, must be the `created_by`) that loads the ExpenseClaim row via `Engine._loadRow("ExpenseClaim", claimId)` (already exists at `Engine.js:470`), reads the saved columns (event_id, expense_date, semester, payout_method, payout_handle), reads the draft's `ClaimLineItems` for `receipt_id` and `budget_line_id`, and returns `{ claim_id, claimant_id, notes, status, total_amount, event_id, expense_date, semester, payout_method, payout_handle, budget_line_id, receipt_ids }`. Also extend `api_getMyClaims` so each draft claim row carries a minimal "is this draft resumable" marker the table needs (a single boolean `draft: status === "DRAFT"` is sufficient, since the per-row Resume click will then call the new `api_getClaimDraft`). The full fields above are NOT added to `api_getMyClaims` to keep the list payload small.
- **Types (types.ts):** add `event_id?`, `expense_date?`, `semester?`, `payout_method?`, `payout_handle?` to the second `Claim` interface (`types.ts:239-249`, the one imported by ClaimsView); add a new response interface `ClaimDraftResponse` carrying the full shape returned by `api_getClaimDraft`.
- **apiService (services/api.ts):** add `getClaimDraft(claimId)` next to `saveClaimDraft` (around `services/api.ts:1391-1413`).
- **ClaimsView.tsx:**
  - In the table body (`ClaimsView.tsx:824-859`), when `c.status === "DRAFT"`, render a new `<button>` (e.g. "Resume") in an additional column or appended to the existing cells. The button calls a new `resumeDraft(c.claim_id)` handler.
  - `resumeDraft(claimId)` calls `apiService.getClaimDraft(claimId)`, populates every form state from the response: `setClaimantId`, `setExpenseDate`, `setSemester`, `setEventId`, `setAmount`, `setNotes`, `setBudgetLineId`, `setPayoutMethod`, then `JSON.parse(payout_handle)` to fill `setFpsPhone`/`setFpsAccount`/`setPaymePhone`/`setOtherDetails`/`setQrFile` based on the `method` field. Set `setDraftId(claimId)` and reuse the same `idempotencyKey` the draft was saved with (returned by the new endpoint) so a subsequent `Save Draft` / `Submit Claim` calls `api_saveClaimDraft` / `api_atomicSubmitClaim` with `claimId` set, hitting the update branch of `api_saveClaimDraft` (`Api.js:1185-1201`) and the atomic submit's draft-first path. Open the modal via `setShowForm(true)` and step the user to the first incomplete step (or `member` for simplicity in v1).
  - Hydrate the receipt list: pre-fill `uploadedReceipts` with `{ receiptId, status: "done" }` placeholders for each `receipt_id` returned (no re-upload — the receipts already exist in Drive; the receipt-display block at `ClaimsView.tsx:402-451` only reads `r.fileName`, `r.vendor`, `r.receiptDate`, `r.receiptTotal`, `r.status`, `r.receiptId`, `r.error`, so the existing `receipt-${r.status}` style works without the file bytes).
  - The existing `openNewClaim` (`ClaimsView.tsx:121-125`) still calls `resetForm()` so a brand-new claim is unaffected.

## Acceptance criteria

- [ ] `api_getClaimDraft(claimId)` exists in `Api.js`, is registered in the server-functions export list, is operator-gated (`_requireOperator`), rejects non-DRAFT claims, and rejects claims where `created_by` is not the calling operator. Returns at minimum: `claim_id`, `claimant_id`, `notes`, `status`, `total_amount`, `event_id`, `expense_date`, `semester`, `payout_method`, `payout_handle`, `budget_line_id` (string or null), `receipt_ids` (array), `uuid` (the saved idempotency key, so the resume can pass it back to `saveClaimDraft`/`atomicSubmitClaim`).
- [ ] `api_getMyClaims`'s per-claim shape includes a `draft: boolean` marker (true iff `status === STATUS.ExpenseClaim.DRAFT`). The existing six fields are unchanged.
- [ ] `types.ts` second `Claim` interface gains optional `event_id`, `expense_date`, `semester`, `payout_method`, `payout_handle`, plus a `draft: boolean`. A new `ClaimDraftResponse` interface exists with the full per-draft shape.
- [ ] `apiService.getClaimDraft(claimId)` exists in `services/api.ts`, follows the same Apps-Script-run pattern as `getMyClaims` (mock fallback for non-Apps-Script hosts), and is exported alongside the rest of the service.
- [ ] `ClaimsView.tsx` table row for any claim with `c.status === "DRAFT"` (or `c.draft === true`) renders a "Resume" button. For non-DRAFT rows, no Resume button renders.
- [ ] Clicking Resume calls `apiService.getClaimDraft(c.claim_id)`, opens the multi-step claim form with `showForm=true`, and pre-populates: `claimantId`, `expenseDate`, `semester`, `eventId`, `amount`, `notes`, `budgetLineId`, `payoutMethod`, and the appropriate `fpsPhone`/`fpsAccount` (FPS) / `paymePhone` (PAYME) / `otherDetails` (OTHER) by parsing the response's `payout_handle`. `draftId` state is set to the draft's `claim_id`, and the `idempotencyKey` is set to the response's `uuid`.
- [ ] The resume form's receipt step pre-populates `uploadedReceipts` with one placeholder entry per `receipt_id` returned by the backend, with `status: "done"` and `receiptId` set, so the existing receipt-display UI at `ClaimsView.tsx:402-451` shows them without a re-upload.
- [ ] After resuming, clicking "Save Draft" again sends `claimId: <draft.claim_id>` and `uuid: <original uuid>` to `apiService.saveClaimDraft` — verified by the existing update branch (`Api.js:1185-1201`) which requires `created_by === operator.userId` and `status === STATUS.ExpenseClaim.DRAFT`; both hold.
- [ ] After resuming, clicking "Submit Claim" calls `apiService.atomicSubmitClaim` with `claimId` set; the existing atomic-submit draft-first path takes over from there.
- [ ] Manual smoke test (the spec's named scenario): a Treasurer opens the form, fills out a Claim through at least the Member + Details steps, clicks "Save Draft", closes the browser tab, reopens the page, sees the DRAFT row in the table, clicks "Resume", the form re-opens with the previously-entered Member, expense date, semester, event, amount, notes, and budget line already populated. The Treasurer does not re-enter already-saved data.
- [ ] Manual smoke test 2: same flow, but for a draft that had `payoutMethod: FPS` saved. After Resume, the FPS phone and FPS account fields are pre-populated.
- [ ] Manual smoke test 3: same flow, but for a draft that had `payoutMethod: PAYME`. After Resume, the PayMe phone field is pre-populated.
- [ ] Manual smoke test 4: a Treasurer who has never saved a draft sees no Resume button anywhere in the table.
- [ ] Manual smoke test 5: clicking Resume on a DRAFT belonging to a different operator is rejected by the backend with `UNAUTHORIZED` (the operator-auth + created_by check).

## Out of scope

- Changing the draft-save data model itself. `api_saveClaimDraft`'s column-write logic (`Api.js:1203-1251`), the `COLS.ExpenseClaims` schema (`Constants.js:137-159`), and the `_paymentHandle` encoding (`Api.js:986-992`) are NOT touched. This ticket only adds a read path for what is already persisted.
- Re-uploading receipt bytes on resume. The existing drafts' receipts remain in Drive and are referenced by `receipt_id`; the receipt-display UI in the form reads `receiptId` from `uploadedReceipts` without needing the file bytes, so the resume shows them as already-uploaded. If a Treasurer wants to replace a receipt on the resumed draft, they remove it and re-add — that flow is unchanged.
- The Event picker gap (free-text `eventId` on `ClaimsView.tsx:53`). That is its own ticket per #59's decision ("Event CRUD: full create/edit (Committee) + correct/close (Treasurer) + list endpoint + picker UI, per ADR 0073"). This ticket only preserves whatever `eventId` value the draft was saved with, including legacy free-text values.
- The P0 `STATUS.APPROVED` bug in `api_getMyClaims` (`Api.js:128-130`). That's ticket #68 / a separate P0 fix; this ticket works around it by not depending on the budget-line filter behaving correctly (Resume works regardless of whether the budget line comes back).
- Backend changes to `api_getMyClaims` beyond adding the `draft: boolean` marker. Specifically: NOT adding the full per-draft field set to `api_getMyClaims`; the Resume click goes through `api_getClaimDraft(claimId)` for the heavy payload.
- Income, Budget Request, or any other entity's draft-resume flow. This ticket is Claims-only.
- A `Discard draft` button. That's a separate UX request, not implied by "Resume."
- Any change to the `Claim` queue or Treasurer review dashboard (`ReviewDashboard.tsx`).
