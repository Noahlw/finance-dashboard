## What to build

Full Event CRUD + picker per ADR 0073. ADR 0073 (accepted) reads: "Committee Operators may create and edit Events. The Treasurer may also correct or close Events. Event changes must preserve existing Claim links and audit history; Event association never merges Claims."

Verified facts (re-checked today, not relying on earlier session citations):

- `Events` schema is already defined in `Constants.js:130-136` (`event_id`, `name`, `semester`, `owner_user_id`, `created_at`) and `Constants.js:25` (`TABS.EVENTS = "Events"`). `ENTITY_PREFIX.Event = "EVENT"` at `Constants.js:326`, so `Ids.nextId("Event")` produces `EVENT-1`, `EVENT-2`, ... This means the data shape is settled; nothing in `Constants.js` changes.
- The only existing Event-touching endpoint is `api_setEventSelections` at `Api.js:3538`. Confirmed: it is `Treasurer only` (line 3545), write-only, called exclusively by `Migration.setEventSelections` for the Annual Migration carry-forward step. Nothing else in `Api.js` reads or writes the `Events` tab today. (Search: `grep api_[a-zA-Z]*[Ee]vent Api.js` returns only `api_setEventSelections`.)
- `ROLES` at `Constants.js:258-263` are `ADVISOR_AUDITOR`, `COMMITTEE`, `MEMBER`, `TREASURER`. ADR 0073's "Committee Operators" maps to `ROLES.COMMITTEE` (the same role gate used by `Api.js:933`'s Budget Request path, which is the canonical "Committee can mutate" pattern).
- Free-text `eventId` inputs confirmed unchanged in both places:
  - `ClaimsView.tsx:53` — `const [eventId, setEventId] = useState("");` on the Claim form, submitted as `eventId` at `ClaimsView.tsx:235` via `submitClaimDraft`/`saveClaimDraft`.
  - `FinanceAccountsView.tsx:476` — `const [eventId, setEventId] = useState("");` inside `RecordIncomeForm`, submitted as `eventId` at `FinanceAccountsView.tsx:495` to `api_recordIncome`.
  - No `EVENTS` join / no `<select>` for events anywhere in either view today.
- Frontend service bridge pattern to mirror: `api.ts:605` `getMembers: () => ... api_getMembers()`, `api.ts:454` `getAccounts: () => ... api_getAccounts()`. New `getEvents` should follow the same shape. `api_setEventSelections` is already bridged at `api.ts:1472` as the only existing precedent.

Backend scope (new endpoints, exported in the existing `api_*` block at the bottom of `Api.js` around line 3824-3863):

- `api_listEvents()` — returns every `Events` row as `{ event_id, name, semester, owner_user_id, created_at, status }` where `status` is a new `STATUS.Event` namespace value (`OPEN`, `CLOSED` — see below). Any authenticated operator (`_requireOperator()` only; no role gate) can read, mirroring the visibility of `api_getAccounts` (`Api.js:2117`) and `api_getMembers` (`Api.js:1033`). Default ordering: most recent `created_at` first.
- `api_createEvent(payload)` — Committee only (`ROLES.COMMITTEE` per `Api.js:933`'s role-check style). Payload: `{ name, semester, owner_user_id }` (all required, non-empty). Allocates `event_id` via `Ids.nextId("Event")` (yields `EVENT-N`), writes `created_at = new Date()`, status `OPEN`. Audit: `Audit.append(operator.userId, "Event", eventId, "CREATE", { name, semester, owner_user_id })`.
- `api_editEvent(payload)` — Committee only. Payload: `{ event_id, name?, semester?, owner_user_id? }`. Only editable while `status === "OPEN"`. Rejects with `ILLEGAL_STATE` if the event is `CLOSED`. Audit: `Audit.append(operator.userId, "Event", eventId, "UPDATE", { changed: { ... } })` where `changed` only includes fields actually modified.
- `api_correctEvent(payload)` — Treasurer only (`ROLES.TREASURER` per the `api_setEventSelections` role-gate pattern at `Api.js:3545`). Same editable field surface as `api_editEvent`. **Editable in both `OPEN` and `CLOSED` states** — this is the Treasurer override path, distinct from `api_editEvent`. Audit: `Audit.append(operator.userId, "Event", eventId, "CORRECT", { changed: { ... } })`.
- `api_closeEvent(payload)` — Treasurer only. Payload: `{ event_id, reason }` (reason required, non-empty, recorded in audit). Sets `status = "CLOSED"`, sets a new `closed_at` column (added to the `Events` schema — see Acceptance criteria). Idempotent: closing an already-`CLOSED` event returns `ILLEGAL_STATE`, not success. Per ADR 0073, `closed` events retain existing Claim links (no cascade, no merge, no force-reassignment). Audit: `Audit.append(operator.userId, "Event", eventId, "CLOSE", { reason })`.

Memoizes / caches the list within the session; no need for SWR/TanStack, this list is small and stable within a session.

Payload submission at `ClaimsView.tsx:235` keeps `eventId` field name; value is now a real `EVENT-N` string from the picker (or `undefined` when "No event" selected). Same for the review-step display at `ClaimsView.tsx:755`.
  - `FinanceAccountsView.tsx:476` — same replacement inside `RecordIncomeForm`. The free-text `<input>` at `FinanceAccountsView.tsx:552-560` becomes the picker. Payload at `FinanceAccountsView.tsx:495` unchanged in field name.
- Committee-facing create/edit UI: a new `EventsView` (e.g. `src/frontend/src/EventsView.tsx`) mounted in `App.tsx`'s view switcher (alongside the other workspace views), gated to `role === ROLES.COMMITTEE || role === ROLES.TREASURER`. Provides:

  - Per-row Edit button (only when `status === "OPEN"`, only for Committee) → same modal pre-populated.
  - Per-row Correct button (Treasurer only) → same fields, allowed in any status.
  - Per-row Close button (Treasurer only) → confirmation modal requiring non-empty reason.
- `App.tsx` wires the new view into the sidebar/bottom-nav (whatever nav surface is appropriate for the operator role, matching how `MembersView` / `DashboardView` are mounted).
- Frontend service additions in `src/frontend/src/services/api.ts`: `getEvents`, `createEvent`, `editEvent`, `correctEvent`, `closeEvent`, each mirroring the existing `google.script.run.withSuccessHandler(...).api_*` shape used by `getMembers` at `api.ts:604-606` and `setEventSelections` at `api.ts:1472`. ## Acceptance criteria

- [ ] `Constants.js` STATUS namespace gains `STATUS.Event = Object.freeze({ OPEN: "OPEN", CLOSED: "CLOSED" })`. `COLS.Events` gains a `status: 6` column and a `closed_at: 7` column. `Setup.js`'s tab initializer (search `getSheet_(TABS.EVENTS)` and any `COLS.Events` row-1 header writer) writes the new header shape so a fresh `setupAll` produces a structurally-correct `Events` tab with header in row 1.
- [ ] `api_listEvents()` is exported in `Api.js`'s `api_*` block, gated by `_requireOperator()` only. Returns `{ ok: true, data: Event[] }` where `Event = { event_id, name, semester, owner_user_id, created_at, status, closed_at? }`. Empty list returns `{ ok: true, data: [] }`, not an error. Unauthorized returns `{ ok: false, error: { code: "UNAUTHORIZED", message: ... } }` matching the existing `_err(...)` envelope.
- [ ] `api_createEvent({ name, semester, owner_user_id })` is exported, Committee-only. Allocates `event_id` via `Ids.nextId("Event")` (yielding `EVENT-N` per `ENTITY_PREFIX.Event = "EVENT"` at `Constants.js:326`). Writes `status = "OPEN"`, `created_at = new Date()`. Audit appends `"CREATE"` with `{ name, semester, owner_user_id }`. Empty/missing required fields return `INVALID_INPUT`, not a silent write. Non-Committee callers receive `UNAUTHORIZED`.
- [ ] `api_editEvent({ event_id, ...fields })` is exported, Committee-only. Only `name`, `semester`, `owner_user_id` are editable. Rejects with `ILLEGAL_STATE` if `status === "CLOSED"`. Audit appends `"UPDATE"` with only the fields that actually changed. Audit does **not** include `event_id`, `created_at`, `status`, or `closed_at`.
- [ ] `api_correctEvent({ event_id, ...fields })` is exported, Treasurer-only. Same editable fields as `api_editEvent`. Allowed in **both** `OPEN` and `CLOSED` states — this is the Treasurer override path. Audit appends `"CORRECT"` with the changed fields.
- [ ] `api_closeEvent({ event_id, reason })` is exported, Treasurer-only. `reason` is required and non-empty (empty → `INVALID_INPUT`). Sets `status = "CLOSED"` and `closed_at = new Date()`. Idempotency: closing an already-`CLOSED` event returns `ILLEGAL_STATE`. Audit appends `"CLOSE"` with `{ reason }`. Per ADR 0073, no Claim or Income row's `event_id` is touched by this call — `grep -n 'event_id' Api.js` still shows zero writes to `ExpenseClaims.event_id` or `Income.event_id` from the close path.

## Out of scope

- Any backfill or migration of historical free-text `eventId` values on existing Claim or Income rows. Per ADR 0180 (#66, accepted), legacy free-text values are **never** auto-backfilled — fuzzy matching was considered and rejected. Manual re-link is permitted only via the picker on the edit form once that path exists, and the edit path on Claims is a separate ticket (#67). This ticket's changes only affect *new* Claim/Income records and *new* Events.
- Income editing generally — there is no `api_editIncome` endpoint today, and per ADR 0180, none is being built here. Income records created via the new picker will have a real `event_id`; legacy free-text Income `eventId` values remain grandfathered permanently with no edit path.
- Claim-side edit-time re-linking of an existing Claim's `event_id`. That is the separate ticket #67 (`api_editClaim` + edit UI accepting `eventId`), which depends on this ticket's picker existing but is its own scope. Do **not** bundle `#67`'s `api_editClaim` changes into this ticket.
- Any `api_deleteEvent` endpoint. ADR 0073 grants create / edit / correct / close only — it does not grant delete, and "Event association never merges Claims" is incompatible with silent deletion. If deletion is ever wanted, it is a separate ADR.
- Changing `api_setEventSelections` (Annual Migration) at `Api.js:3538`. That endpoint is the migration carry-forward path, already works on `event_id` strings, and is unrelated to day-to-day Event CRUD. Its semantics, role gate (`Treasurer` only), and call site in `Migration.setEventSelections` stay exactly as they are.
- Changes to the `Events` column layout beyond what the schema extension above requires (`status`, `closed_at` additions). `event_id`, `name`, `semester`, `owner_user_id`, `created_at` keep their existing positions.
- A separate `Event` audit namespace beyond what `Audit.append(...)`'s existing `entity`/`entityId`/`action` fields already carry. The existing `Audit.append(userId, "Event", eventId, "CREATE"|"UPDATE"|"CORRECT"|"CLOSE", details)` shape handles all four event-mutation actions.
- UI work unrelated to Events in `App.tsx`, `DashboardView.tsx`, `BudgetRequestsView.tsx`, `MembersView.tsx`, `PayoutsView.tsx`, `ReportsView.tsx`, `ReconciliationView.tsx`, `ReviewDashboard.tsx`, `MigrationWizard.tsx`. This ticket touches only `ClaimsView.tsx`, `FinanceAccountsView.tsx`, `App.tsx` (view-switcher wiring), the new `EventsView.tsx`, the new `EventPicker.tsx` component, `services/api.ts`, and `types.ts`.
- Tests for browser/E2E picker rendering beyond what is required to prove "picker shows events" / "picker replaces free-text input" once — that broader suite is tracked in #62 and not duplicated here.
