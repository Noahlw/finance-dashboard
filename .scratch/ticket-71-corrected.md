## What to build

Eight confirmed mutating endpoints in `Api.js` accept calls from anyone with a Google session and a known email, without going through the project's standard active-status/role gate (`_requireOperator()` at `Api.js:920-944`). The original audit inventory had nine entries; `api_resolveSession` was verified to be the one non-gap and is documented below. `_requireOperator()` checks, in order: session present (`Session.getActiveUser().getEmail()`), user resolves (`_resolveUser`), role is `COMMITTEE` or `TREASURER` (`Api.js:933`), and the user row's `active` flag is truthy (`Api.js:938`). Every other mutating endpoint in the file already uses it.

This ticket closes those gaps. For each endpoint below, replace the inline `email` + `_resolveUser(email).isUnknown` early-return (or, for endpoints 8 and 9, the existing Treasurer-role check) with a call to `_requireOperator()`, preserving any existing ownership/status checks. Where an endpoint mutates a record owned by a specific user and currently lacks an ownership check, add one before the write.

The nine endpoints and their current state (each line cited verified against the current `Api.js`):

1. **`api_resolveSession` (`Api.js:57-92`)** — endpoint #1 is NOT a gap. It is the session-bootstrap endpoint and itself implements the role + active check inline (`Api.js:70` role check, `Api.js:75` active check). It cannot call `_requireOperator()` because that helper is what `api_resolveSession` would otherwise depend on; calling it would create a circular bootstrap. **Dropped from this ticket's acceptance criteria; listed here for the record so the next reader does not re-flag it.**
2. **`api_uploadReceipt` (`Api.js:165-263`)** — only checks `email` (`Api.js:173-176`) and `!user.isUnknown` (`Api.js:177-180`). No role check, no active check. Any registered user (including a Member) can upload a receipt.
3. **`api_editClaim` (`Api.js:539-592`)** — checks `email` (`Api.js:540-543`), `!user.isUnknown` (`Api.js:544-547`), claimant-owns-this-row (`Api.js:557-559`), and status === SUBMITTED (`Api.js:560-562`). No role check, no active check. A registered Member can edit their own SUBMITTED claim. The status check already blocks editing of DRAFT/NEEDS_INFO claims (so today's code does not, in fact, permit editing another user's DRAFT/NEEDS_INFO claim — the earlier-session note about that was a misremembering of the current state; the real, current gap is the missing `_requireOperator()`).
4. **`api_saveBudgetRequestDraft` (`Api.js:662-773`)** — checks `email` (`Api.js:663-666`) and `!user.isUnknown` (`Api.js:667-670`). No role check, no active check, no ownership check on `payload.request_id` (an attacker who knows another user's request id could overwrite it).
5. **`api_submitBudgetRequest` (`Api.js:778-823`)** — checks `email` (`Api.js:779-782`) and `!user.isUnknown` (`Api.js:783-786`). No role check, no active check, no ownership check (an attacker could submit anyone else's draft).
6. **`api_discardBudgetRequest` (`Api.js:828-849`)** — checks `email` (`Api.js:829-832`) and `!user.isUnknown` (`Api.js:833-836`). No role check, no active check, no ownership check.
7. **`api_deleteOrphanedReceipt` (`Api.js:270-305`)** — checks `email` (`Api.js:271-274`), `!user.isUnknown` (`Api.js:275-278`), and that the receipt's `uploaded_by` matches the caller (`Api.js:285-290`). No role check, no active check. Any registered user (including Member) who happens to have uploaded a receipt can delete it.
8. **`api_getPendingBudgetRequests` (`Api.js:854-886`)** — checks `email` (`Api.js:855-858`) and `user.isUnknown || user.role !== ROLES.TREASURER` (`Api.js:860-862`). Missing the `user.active` check. An inactive Treasurer still receives the pending list.
9. **`api_decisionBudgetRequest` (`Api.js:893-914`)** — checks `email` (`Api.js:894-897`) and `user.isUnknown || user.role !== ROLES.TREASURER` (`Api.js:898-901`). Missing the `user.active` check. An inactive Treasurer can still approve/reduce/reject/close budget requests. Note: the actor passed to `Engine.transition` is `user.userId` from session (`Api.js:907`), not a caller-supplied field, so the earlier-session concern about a caller-supplied `committeeYear`/actor was a misremembering; the only auth gap here is the missing active check.

No additional unguarded mutating endpoints were found. Every other `api_*` function in `Api.js` already calls `_requireOperator()` (verified by line-by-line scan against the current file: 60+ call sites, see `Api.js:96, 313, 1035, 1065, 1136, 1168, 1330, 1396, 1438, 1911, 2001, 2026, 2053, 2080, 2119, 2152, 2196, 2232, 2272, 2312, 2353, 2378, 2402, 2427, 2466, 2503, 2534, 2573, 2605, 2642, 2685, 2713, 2739, 2912, 3196, 3360, 3372, 3385, 3407, 3431, 3443, 3457, 3478, 3499, 3520, 3541, 3562, 3583, 3604, 3626, 3640, 3661, 3682, 3700, 3714, 3744, 3758`).

## Acceptance criteria

- [ ] **`api_uploadReceipt` (`Api.js:165`) calls `_requireOperator()` first**, replacing the existing `email`/`!isUnknown` early-return (`Api.js:173-180`). On any caller whose `_requireOperator()` would throw (no session, unknown user, role not in {COMMITTEE, TREASURER}, or `user.active === false`), the endpoint returns the same `_err("UNAUTHORIZED", ...)` envelope `_requireOperator()` produces and writes an audit denial via `_auditAuthDenied`. Receipt upload then never reaches the hash-scan or Drive-write path. Test scenario: an inactive Treasurer-role user with a valid session whose `Users.active` flag is `false` calls the endpoint with valid args → receives an UNAUTHORIZED error and no receipt row or Drive file is created.
- [ ] **`api_editClaim` (`Api.js:539`) calls `_requireOperator()` first**, replacing the existing `email`/`!isUnknown` early-return (`Api.js:540-547`). The existing ownership check (`Api.js:557-559`) and SUBMITTED-status check (`Api.js:560-562`) remain unchanged and run after the auth gate. Test scenario: a Member-role user with `active=true` who owns a SUBMITTED claim calls the endpoint → receives UNAUTHORIZED before the ownership loop is reached. A second scenario: an inactive Committee-role user who owns the claim → also UNAUTHORIZED.
- [ ] **`api_saveBudgetRequestDraft` (`Api.js:662`) calls `_requireOperator()` first**, replacing the existing `email`/`!isUnknown` early-return (`Api.js:663-670`). When `payload.request_id` is provided and resolves to an existing BudgetRequest row, additionally verify the row's `requester_id` equals `user.userId` and return `_err("UNAUTHORIZED", ...)` otherwise — this is the missing ownership check. Test scenario: an active Treasurer-role user who is not the requester passes a known `payload.request_id` belonging to another user → receives UNAUTHORIZED, the existing BudgetRequests row is unchanged, and no BudgetRequestLines rows are rewritten.
- [ ] **`api_submitBudgetRequest` (`Api.js:778`) calls `_requireOperator()` first**, replacing the existing `email`/`!isUnknown` early-return (`Api.js:779-786`). Add the missing ownership check: after `Engine._loadRow("BudgetRequest", requestId)` succeeds, verify `row.values[COLS.BudgetRequests.requester_id - 1] === user.userId` and return `_err("UNAUTHORIZED", ...)` otherwise. Test scenario: an active Committee-role user who is not the requester calls the endpoint with another user's draft id → receives UNAUTHORIZED and the draft stays in DRAFT.
- [ ] **`api_discardBudgetRequest` (`Api.js:828`) calls `_requireOperator()` first**, replacing the existing `email`/`!isUnknown` early-return (`Api.js:829-836`). Add the missing ownership check: after `Engine.transition("BudgetRequest", requestId, "WITHDRAW", ...)` returns, ensure the transition was authorized for this operator — since `Engine.transition` enforces state-machine validity but not row ownership, the cleanest fix is to load the row first and verify `requester_id === user.userId` before calling `Engine.transition`. Test scenario: an active Committee-role user who is not the requester calls the endpoint with another user's draft id → receives UNAUTHORIZED and the draft is not withdrawn.
- [ ] **`api_deleteOrphanedReceipt` (`Api.js:270`) calls `_requireOperator()` first**, replacing the existing `email`/`!isUnknown` early-return (`Api.js:271-278`). The existing uploader-owns-this-row check (`Api.js:285-290`) remains unchanged and runs after the auth gate. Test scenario: a Member-role user with `active=true` who originally uploaded the receipt calls the endpoint with the receipt's id → receives UNAUTHORIZED before the Drive-trash path runs. A second scenario: an inactive Committee-role user who uploaded the receipt → also UNAUTHORIZED.
- [ ] **`api_getPendingBudgetRequests` (`Api.js:854`) calls `_requireOperator()` first**, replacing the existing `email`/`!isUnknown || role !== TREASURER` early-return (`Api.js:855-862`). Test scenario: a Treasurer-role user with `Users.active === false` calls the endpoint → receives UNAUTHORIZED and no pending requests are returned.
- [ ] **`api_decisionBudgetRequest` (`Api.js:893`) calls `_requireOperator()` first**, replacing the existing `email`/`!isUnknown || role !== TREASURER` early-return (`Api.js:894-901`). Test scenario: a Treasurer-role user with `Users.active === false` calls the endpoint with `action="APPROVE"` and a valid pending request id → receives UNAUTHORIZED, the request stays PENDING, and no `BudgetRequest` transition audit row is written.
- [ ] All listed endpoint test scenarios above are reproducible: each requires running the endpoint against a controlled test session (`Session.getActiveUser().getEmail()` returning a specific known email, with the corresponding `Users` row pre-seeded to the desired role/active combination). The current test harness does not exercise `Session.getActiveUser`, so this ticket either (a) adds a thin test seam (e.g. a `_resolveUser` shim or per-call override) sufficient to drive these scenarios, or (b) documents in `docs/specs/committee-finance-web-app.md` the manual reproduction recipe for each scenario. Pick (a) if the seam costs <50 lines and is non-invasive; otherwise (b).
- [ ] After the fix, the total number of `_requireOperator()` call sites in `Api.js` is at least 68 (60 existing + 8 newly added; `api_resolveSession` is intentionally excluded — see note in "What to build" above). `grep -c "_requireOperator" Api.js` returns the expected count.

## Out of scope

- Redesigning the auth model. This ticket only closes the gaps in the listed endpoints; it does not change `_requireOperator()` itself, does not introduce new roles, and does not alter the meaning of `user.active`.
- `api_getMyBudgetRequests` (`Api.js:601-657`) and `api_getMyClaims` (`Api.js:94-159`). These are read endpoints and return data scoped to the caller; the P0 logic defect in `api_getMyClaims` (`Api.js:128-130`) is a separate ticket.
- `api_resolveSession` (`Api.js:57-92`). Already implements role + active inline; documented in "What to build" only to prevent re-flagging.
- The P0-A `api_uploadReceipt` hash check-then-append race (`Api.js:197-262`) — that is a separate ticket tracked under the #59 P0-A blocker.
- The P0 `api_getMyClaims` undefined `STATUS.APPROVED` comparison (`Api.js:128-130`) — separate ticket.
- Any non-`Api.js` mutation paths (frontend-only state, Discord retries, etc.). The audit only flagged the backend endpoints.
- Adding a generic "session impersonation for tests" framework. If test-seam work (criterion above) grows beyond ~50 lines, defer it to a follow-up ticket and document manual repro instead.
